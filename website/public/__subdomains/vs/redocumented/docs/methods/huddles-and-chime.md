# Huddles, the realtime (RTM-style) gateway, and the AWS Chime media layer

**Provenance: source-read only. None of this was live-tested by this project.**
Everything below comes from reading two independent open-source projects that
join Slack Huddles in production, plus AWS's public Chime SDK docs. It is
recorded so the shape is not lost; treat it as a strong lead, not as verified
behavior. Per this catalog's ethos: `verified` levels for the methods below
stay at `existence-only`, and the added params/response fields are marked as
third-party-sourced.

## The short version

- A Huddle's **signalling and state** live in Slack: `rooms.*` / `screenhero.*` /
  `huddles.*` Web API methods plus a websocket event stream.
- A Huddle's **audio/video media** does not go through Slack's servers. Slack
  hands the client an **AWS Chime SDK meeting** (the response key is called
  `free_willy`), and the client talks to Chime directly using the stock
  `amazon-chime-sdk-js`. huddlefm exposes the region as `CHIME_MEDIA_REGION`
  (default `ap-southeast-2`); huddlecast defaults to `us-west-1`.
- Both projects only ever handle the Chime path. Neither documents any
  non-Chime huddle backend, which is consistent with "all huddles go through
  AWS" but is not proof of it for every workspace or every call type.
  `screenhero.rooms.info` responses do carry `media_backend_type` and
  `media_server` fields, whose possible values we have not seen enumerated.

## Auth model these projects use

Both use a **browser-session** identity, not a bot/app token:

- `xoxc-…` client token plus the `d` cookie (`xoxd-…`), sent as
  `Cookie: d=<value>` with `token=<xoxc>` in the form body, POSTed to
  `https://<workspace>.slack.com/api/<method>` (not `slack.com/api`).
- huddlecast needs only the `d` cookie: it `GET`s `https://<host>/` and
  regex-extracts `"api_token":"xoxc-…"` from the boot HTML, caching it about
  45 minutes. Rejection surfaces as `not_authed` / `invalid_auth` /
  `token_expired`, or a redirect to `/signin` in the boot HTML.
- Both add client-mimicking fields: `_x_reason` (a free-text tag such as
  `calls-api/<method>`, `respond-to-huddle-invite`,
  `all-calls-store/conditional-fetch`), `_x_mode=online`, `_x_app_name=client`,
  and (huddlefm) `_x_sonic=true`. Whether any of these are required is
  unknown; they mirror what the real client sends.
- On Enterprise Grid huddlecast notes `conversations.list` is blocked for this
  identity and falls back to `client.counts` + `conversations.info`.

## Web API methods

### `rooms.join` — join (or start) a huddle in a channel

Params seen: `channel_id`, `regions` (Chime media region to request, e.g.
`ap-southeast-2`, `us-west-1`), `multidevice` (`"true"` in huddlefm, `"false"`
in huddlecast; meaning unconfirmed), `token`.

Response fields these projects read (partial, not a full schema):

```
ok
call.call_id                       // the room/call id
call.free_willy.meeting            // Chime Meeting object (see below)
call.free_willy.attendee           // Chime Attendee object (see below)
canvas.thread_channel_id           // channel holding the huddle's thread
canvas.root_thread_ts              // ts of the huddle thread root
huddle.id
huddle.created_by
huddle.participants                // user ids, OR objects with .user_id
```

huddlefm deletes `meeting.MeetingFeatures` when it is `null` before handing
the object to the Chime SDK (presumably because the SDK does not accept a null
there; the code does not say why).

### `screenhero.rooms.info` — read a room's state

Param: `room` (the call id). "Screenhero" is Slack's older name for the
calls/huddles subsystem and survives in method names.

huddlefm uses it to join an **invited** huddle (the `huddle_invite` event
carries the `free_willy` blob; this call supplies the rest). It also sends
`_x_reason=all-calls-store/conditional-fetch`.

Fields read: `room.id`, `room.created_by`, `room.participants`,
`room.thread_root_ts` / `room.canvas_thread_ts`, `room.has_ended`,
`room.date_end`, and (huddlecast) `participants_screenshare_on`,
`participants_camera_on`, `channels`, `huddle_link`. The typed client lists
many more (`pending_invitees`, `knocks`, `recording`, `media_backend_type`,
`is_scheduled`, …).

### `rooms.inviteResponse` — answer a huddle invite

Params: `response` (`"decline"` seen; accept value not seen), `channel_id`,
`room_id`, plus `_x_reason=respond-to-huddle-invite`. huddlefm declines
invitations to channels it cannot access.

### `huddles.get`, `huddles.history`, `huddles.getTrackUrls`, `huddles.knock`, …

Already catalogued (see `datamine-2026-09.md` and `internal-canvas-2026.md`).
Typed params exist for `huddles.get` (`huddle_id`) and `huddles.history`
(`limit`, `missed_huddles_only`, `users`, `users_only`) from
`slack-undoc-client`; neither huddlefm nor huddlecast calls them. Names only
for the rest.

### Supporting calls these bots make

`conversations.info`, `conversations.join`, `conversations.create`,
`conversations.setTopic`, `conversations.invite`, `conversations.kick`,
`conversations.replies`, `reactions.add`, `reactions.remove`, `auth.test`
(all documented methods, called with the xoxc/d identity), and
`channels.prefs.set` (`channel_id`, `prefs` as a JSON string, e.g.
`who_can_post`, `can_thread`, `enable_at_here`, `enable_at_channel`;
huddlefm uses it to restrict posting in the private companion "controls" channel it creates).

## The realtime websocket (RTM-style, but not `rtm.connect`)

The huddle events arrive on the same **client realtime gateway** the web/desktop
app uses, not the classic bot RTM flow (`rtm.connect` / `rtm.start`, which are
deprecated for apps). huddlefm connects directly:

```
wss://wss-primary.slack.com/?token=<xoxc>
    &sync_desync=1
    &slack_client=desktop
    &start_args=?agent=client&org_wide_aware=true&eac_cache_ts=true&cache_ts=0&name_tagging=true&only_self_subteams=true&connect_only=true&ms_latest=true
    &no_query_on_subscribe=1
    &flannel=3
    &lazy_channels=1
    &gateway_server=T<team_id minus its first letter>-1
    &enterprise_id=<id from auth.test>
    &batch_presence_aware=1
Cookie: d=<xoxd>
```

`gateway_server` and `enterprise_id` are derived from the `team_id` that
`auth.test` returns (huddlefm's variable is misleadingly named `enterpriseId`).
Protocol details seen: server sends `{"type":"hello"}` once ready; client
sends `{"type":"ping","id":<ms>}` every 5 s; server may send
`{"type":"reconnect_url","url":…}` which the client uses for the next
reconnect; reconnect uses exponential backoff capped at 30 s.

Event types huddlefm consumes:

| Event `type` | Fields used | Meaning |
|---|---|---|
| `huddle_invite` | `channel_id`, `call_id`, `sender_user_id`, `free_willy` | Someone invited this user; includes the Chime meeting/attendee blob. |
| `sh_room_join` | `user`, `call_id` or `room.call_id`/`room.id`/`huddle.id` | A participant joined. |
| `sh_room_leave` | same | A participant left. |
| `sh_room_update` | `huddle.has_ended` / `huddle.date_end`, `room.call_id` / `huddle.id` | Room state changed; ended when either end marker is set. |
| `message` (subtype `huddle_thread`) | `room.id`, `room.participants`, `room.has_ended`, `room.date_end` | The thread root of a huddle carries a `room` object. |
| `message` (thread reply / IM) | usual message fields | Used for the bot's control UI, not huddle state. |
| `channel_left`, `member_joined_channel`, `member_left_channel` | `channel`, `user` | Membership tracking. |

huddlecast instead **polls** `screenhero.rooms.info` rather than using the
websocket, which is a useful fallback if the gateway is unavailable.

## The Chime layer

What `rooms.join` returns under `call.free_willy` is a standard AWS Chime SDK
pair. Field names, as huddlecast decodes them:

```
meeting:  MeetingId, MediaRegion, ExternalMeetingId, MediaPlacement{…}
          (+ MeetingFeatures, null in observed responses -> strip it)
attendee: AttendeeId, ExternalUserId, JoinToken, Capabilities{…}
```

`MediaPlacement` is the usual Chime endpoint set (audio host, signalling,
TURN control, screen data/viewing/sharing URLs, event ingestion; see AWS
docs). These are short-lived, per-attendee credentials: `JoinToken` is a
secret and should be treated like a session token.

How the projects use it (both run the real SDK inside headless Chromium, not
a reimplementation of the protocol):

1. Load `amazon-chime-sdk-js` (huddlecast bundles v3.32.0) in a page.
2. `new MeetingSessionConfiguration(meeting, attendee)`, then
   `new DefaultMeetingSession(configuration, logger, deviceController)`.
3. huddlefm: `audioVideo.setAudioProfile(AudioProfile.fullbandMusicStereo())`,
   `startAudioInput(<WebAudio MediaStreamDestination stream>)`,
   `audioVideo.start()`, `realtimeUnmuteLocalAudio()`. It can also
   `startVideoInput` + `startLocalVideoTile` to show album art/lyrics as a
   "camera".
4. huddlecast: content share / video send, fed from a WHEP source.
5. Speaking detection ("auto-duck") uses the SDK's
   `realtimeSubscribeToVolumeIndicator` and
   `realtimeSubscribeToAttendeeIdPresence`.
6. Leave with `audioVideo.stop()`.

Chromium is launched with fake-media flags (`--use-fake-ui-for-media-stream`,
`--autoplay-policy=no-user-gesture-required`, tab-capture auto-accept) so no
prompts block the headless page.

Because media is plain Chime, anything the AWS SDK supports (volume
indicators, attendee presence, content share, data messages) is in principle
available to a huddle client; what Slack *permits* an attendee to do is
governed by the `Capabilities` object on the attendee, which we have not seen
populated.

## Safety

`rooms.join` **joins a real call as a real user and is visible to participants**.
Do not call it, `rooms.inviteResponse`, or the websocket against a real account
without a human in the loop, and never with credentials you do not own. Using a
browser-session identity to drive a bot may violate your workspace's rules;
both projects above run it on a dedicated account for that reason.
